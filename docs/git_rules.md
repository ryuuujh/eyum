# E:YUM 개발 규칙

## 1. 커밋 규칙

### 기본 원칙

- 커밋 하나에는 **한 가지 작업 목적**을 담는다. 예를 들어 식품 라벨링 명세 작성과 사이드바 오류 수정은 각각 커밋한다.
- 커밋 전 변경 내용을 읽고, 이번 작업에 필요한 파일만 스테이징한다.
- 코드나 규칙을 바꿨으면 관련 개인 프롬프트 기록(`prompt_log.md`)과 검증 기록(`validation.md`)을 같은 커밋에 포함한다.
- **스테이징·커밋·푸시는 담당자가 직접 수행한다.** AI는 개인 기록을 갱신하고 변경 요약과 커밋 제목을 제안한다.

### 커밋 메시지 형식

```text
유형: 한국어 변경 내용
```

유형은 영문 소문자로 쓴다. 콜론 뒤에 한 칸을 띄우고, **어느 기능에서 무엇을 바꿨는지** 한국어로 적는다. `수정`, `최종`, `완료`, `작업함`처럼 변경 대상을 알 수 없는 제목은 피한다.

| 유형 | 사용 목적 | E:YUM 예시 |
|---|---|---|
| `feat` | 새로운 기능 추가 | `feat: 외박스 라벨 미리보기 추가` |
| `fix` | 오류 수정 | `fix: 라벨링 탭 이동 시 선택한 수출국이 초기화되는 오류 수정` |
| `style` | 화면 디자인·스타일 조정 | `style: 모바일 제품 목록의 행 간격 조정` |
| `refactor` | 동작을 유지하며 코드 구조 개선 | `refactor: 구성품 영양값 환산 함수를 별도 파일로 분리` |
| `docs` | 명세·팀 문서·개인 작업 기록 수정 | `docs: 식품 라벨링 기능 명세 초안 작성` |
| `test` | 테스트 추가·수정 | `test: 구성품 실중량 누락 시 환산 보류 사례 추가` |
| `chore` | 개발환경·의존성·배포 설정 변경 | `chore: 팀 공통 Node.js 버전 설정 추가` |
| `data` | 공유용 가상 데이터 추가·수정 | `data: 제품 등록 테스트용 가상 원재료 목록 추가` |

### 커밋 전 확인

- [ ] `git status`에서 현재 브랜치가 내 기능 브랜치(`feature/…`)인지 확인했다.
- [ ] `git diff --cached`로 이번 커밋에 담긴 내용을 읽고 다른 팀원의 파일이나 공통 파일에 의도치 않은 변경이 없는지 확인했다.
- [ ] 변경한 기능을 검증하고 실제 확인 결과를 기록했다. 실행하지 못한 항목은 **미검증**으로 적었다.
- [ ] 관련 개인 기록 두 파일을 갱신했고, 기능의 입력·출력·동작이 바뀌었다면 해당 `feature_spec.md`도 갱신했다.
- [ ] 실제 환경변수, 인증 정보, 개인정보, 기업 원본 자료가 빠졌는지 확인했다.
- [ ] 설치·빌드 결과, 캐시, 임시 파일, 전달용 ZIP, 로컬 DB가 빠졌는지 확인했다.

### Git에 포함하지 않는 파일

| 구분 | E:YUM에서 제외할 예 |
|---|---|
| 실제 설정과 인증 정보 | `.env`, `.env.local`, 비밀 키 파일(`*.pem`, `*.key`), API 키·토큰·비밀번호가 적힌 파일 |
| 설치·빌드·검사 결과 | `node_modules/`, `.next/`, `out/`, `coverage/`, `*.tsbuildinfo`, `*.log` |
| 기업·개인 자료와 로컬 데이터 | 기업 원본, 개인정보가 담긴 서류, 업로드 파일, 로컬 DB·백업. 프로젝트의 `private_data/`, `uploads/`, `db_backups/` 폴더는 Git 제외 대상으로 설정돼 있다. |
| 개인 작업용 파일 | 임시 파일과 전달용 ZIP. 파일명에 따라 Git에 표시될 수 있으므로 스테이징 목록을 직접 확인한다. |

**팀이 공유하는 파일**은 `.gitignore`, 실제 값이 비어 있는 `.env.example`, `package.json`, `package-lock.json`, 공유하기로 한 가상 테스트 자료다. 공통 패키지를 추가하거나 버전을 바꾸면 `package.json`과 `package-lock.json`을 함께 커밋한다.

제품 예시에는 가상 제품명, 원재료, 원산지, 영양 수치와 라벨 문구를 사용한다. 혜윰에서 받은 실제 값은 라벨에 공개되는 항목도 팀 드라이브에 보관한다. 로컬 seed, 화면 예시, 테스트, 명세, 작업 기록과 PR 본문에도 같은 기준을 적용한다.

## 2. `develop`에 PR 보내기

1. 담당자가 자신의 `feature/…` 브랜치를 푸시한다.
2. GitHub에서 PR을 열고 **base는 `develop`**, **compare는 내 기능 브랜치**로 선택한다. 예를 들어 라벨링은 `feature/labels`에서 `develop`으로 보낸다.
3. PR 본문에는 **변경 목적, 실제 확인 결과, 미검증 항목, 관련 개인 기록 경로**를 적는다. 패키지·환경변수·DB·공통 화면이나 다른 기능에 미치는 영향도 적는다.
4. PR 검토는 유정현이 주담당, 채주현이 부담당이다. `develop`에서 통합 검증을 마친 발표 버전을 `main`에 반영한다.
